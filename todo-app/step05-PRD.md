# STEP 5. PRD.md — "무엇을 만들지" 정하기 (PLAN P-04)

> **PRD.md** = **무엇을 만들지** 정한 요구 문서. AI가 초안을 쓰고 **사람이 판정·확정**해요.

## 📚 이 단계에서 참고하는 파일

| 참고 파일 | 무엇을 가져오나 | 왜 참고하나 |
|---|---|---|
| DECISIONS.md | D-001 (할 일 카드, 상태 변경, AI 기능 없음) | PRD는 **결정의 범위 안에서만** 요구를 정해요. D-001과 충돌하는 후보(AI 추천 등)는 제외해요. |
| PLAN.md | P-04 작업과 완료 조건 | 지금 하는 작업이 무엇이고 **언제 끝인지** 확인해요. |
| README.md | 한 줄 소개 | PRD의 "한 문장 설명"이 README 소개와 **같은 말**을 하게 해요. |
| AGENTS.md | "결정은 사람이 한다" | AI가 요구사항을 **대신 확정하지 않게** 해요. |

## 🔗 이 파일을 나중에 참고하는 곳

| 파일·단계 | 무엇을 가져가나 |
|---|---|
| STEP 6 ARCHITECTURE | Must 기능, 비기능 → 필요한 부품 |
| STEP 7 SCREEN-SPEC | 사용자 스토리, 인수 조건 → 화면과 상태 |
| STEP 8 DATA-MODEL | 4. Task 카드 정보와 상태 규칙 → 저장할 필드 |
| STEP 9 API-SPEC | 사용자 행동, 실패 조건 → 주문서 |
| STEP 10 TEST-PLAN | 인수 조건 → 시험 문제와 정답 |

---

## 🧸 쉽게 말하면

PRD는 **생일 케이크 주문서**예요.

```
🎂 케이크 주문서
  누가 먹나요?        → 8살 동생
  왜 필요해요?        → 생일 파티
  꼭 있어야 할 것     → 초콜릿 맛, 초 8개
  나중에 해도 될 것   → 이름 글씨 장식
  안 할 것           → 과일 (동생이 싫어함)
  받았을 때 확인할 것 → 초 8개가 꽂혀 있나?
```

PRD는 **P**roduct **R**equirements **D**ocument, "제품 요구 문서"예요.

---

## ❓ 왜 필요할까?

| PRD가 없으면 | PRD가 있으면 |
|---|---|
| AI가 "좋아 보이는" 기능을 잔뜩 넣음 | **꼭 필요한 것(Must)**만 먼저 만듦 |
| 다 만들고 나서 "이게 아닌데?" | 만들기 전에 합의 |
| 언제 끝난 건지 모름 | **인수 조건**(확인할 것)이 있음 |

> PRD는 **한 번에 쓰지 않아요.** 여러 번 대화하며 조금씩 채워요.

```
5-0 PLAN 시작 표시
5-1 AI가 질문하고 내가 답하기
5-2 요구사항 후보 받기 (R-001, R-002 …)
5-3 후보마다 판정하기 → 중요한 판정은 DECISIONS에도 (함께 고치기)
5-4 본문 채우기
5-5 열린 질문 정리
5-6 검토하고 확정 → README·PLAN 함께 고치기
```

### 5-0. PLAN에 시작 표시

```claude-code
PLAN.md의 P-04(PRD 작성)를 시작합니다. 상태를 "진행 중"으로 바꾸고 바뀐 줄만 보여 주세요.
```

### 5-1. AI가 질문하게 하기

- claude-code 입력
```claude-code
DECISIONS.md의 D-001과 PLAN.md의 P-04를 읽으세요. 할 일 카드 웹앱의 요구사항을 정하려고 합니다.
D-001과 다른 방향의 기능은 제안하지 마세요. 제가 아직 모르는 것을 대신 정하지 마세요.
요구사항을 정하기 위해 필요한 질문을 가장 중요한 것부터 한 번에 하나씩 물어봐 주세요.
제가 잘 모르면 쉬운 설명과 선택지를 주되, 대신 결정하지 마세요.
```

**이 문장을 넣는 이유**

| 문장 | 이유 |
|---|---|
| "D-001과 다른 방향은 제안하지 마세요" | 결정 범위 안에서만 요구를 정하게 |
| "한 번에 하나씩" | 질문 10개를 한꺼번에 받으면 대충 답하게 됨 |
| "대신 결정하지 마세요" | 모르는 건 설명만 듣고 **내가** 고름 |

**대화 예시**
> **AI**: 첫 질문입니다. 이 앱은 누가 쓰나요? ① 혼자 쓰는 개인 ② 팀이 함께 씀
> **나**: 혼자 쓰는 개인이요.
> **AI**: 카드에 제목 말고 설명도 쓸 수 있게 할까요? 설명은 꼭 써야 하나요?
> **나**: 설명은 써도 되고 안 써도 되게요.
> **AI**: 완료한 카드를 다시 "진행 중"으로 되돌릴 수 있게 할까요?
> **나**: 음… 둘의 차이를 설명해 줄래요?

> 💡 **모르는 건 "설명해 줘"라고 말하는 게 정답이에요.** 모르고 "네"라고 하면 나중에 고치기 어려워요.

| R-002 | 카드 상태를 할 일→진행 중→완료로 바꾼다 | 사용자 답변 | 검토 필요: 완료 후 되돌리기? | D-001 |
| R-003 | 설명은 선택 입력 | 사용자 답변 | 검토 필요 | |
| R-004 | 팀원을 초대한다 | **AI 제안** | 검토 필요 | |

```claude-code
PRD의 R-002 "관련 결정" 칸에도 D-002를 적으세요. 바뀐 두 파일의 줄만 보여 주세요.
```

### 5-4. PRD 본문 채우기

본문의 칸은 **각각 하나의 질문**에 답해요.

| 칸 | 답하는 질문 | 예시 답 |
|---|---|---|
| 1. 한 문장 설명 | 누가, 어떤 문제를, 어떻게 해결해? | 할 일을 자주 잊는 개인이 카드로 등록하고 상태별로 보는 웹앱 |
| 2. 사용자와 사용 상황 | 누가 언제 써? | 혼자, 하루 할 일을 정리할 때 |
| 3. 목표와 성공 확인 | 무엇이 좋아져야 하고, 무엇을 보면 알아? | 할 일을 한곳에서 본다 → 등록한 카드가 목록에 보인다 |
| 4. Task 카드 정보와 상태 규칙 | 카드에 뭐가 있고 상태는 어떻게 바뀌어? | 제목(필수), 설명(선택), 상태 3개, 완료→진행 중 가능(D-002) |
| 5. 범위 | 꼭 / 나중에 / 안 할 것은? | Must: 등록·보기·수정·상태 변경·삭제·새로고침 유지 / Later: 팀 초대 / 안 함: AI 기능 |
| 6. 사용자 스토리와 인수 조건 | 다 됐는지 어떻게 확인해? | 아래 설명 |
| 7. 비기능 요구사항 | 어떤 품질로? | 비밀번호 저장 안 함, 키보드로 입력 가능, 실패하면 알려 줌, 새로고침 뒤 유지 |

#### ⭐ 인수 조건 쓰는 법 (4가지 경우)

| 경우 | 질문 | 확인할 것 (카드 등록 US-01) |
|---|---|---|
| 정상 | 제대로 하면? | 제목을 쓰고 저장하면 "할 일" 칸에 카드가 생긴다 |
| 빈 결과 또는 경계 | 아무것도 없거나 끝자락이면? | 카드가 하나도 없으면 "카드가 없어요"가 보인다 |
| 잘못된 입력 | 잘못 넣으면? | 제목이 비었거나 띄어쓰기만 있으면 저장되지 않고 이유가 보인다 |
| 실패 | 저장이 안 되면? | 성공한 것처럼 보이지 않고, 쓴 내용이 남아 있고, 다시 시도할 수 있다 |

> 💡 **"잘 된다"는 인수 조건이 아니에요.**
> ❌ 등록이 잘 된다 → ✅ "할 일" 칸에 내가 쓴 제목의 카드가 보인다

- claude-code 입력
```claude-code
판정이 끝난 요구사항만 사용해서 PRD.md 본문 1~7을 채워 주세요.
- 문장마다 근거가 된 요구사항 번호(R-)나 결정 번호(D-)를 적으세요.
- 1. 한 문장 설명은 README.md 소개와 같은 뜻이 되게 쓰세요.
- 제외한 R-004, R-005는 기능으로 넣지 마세요. R-004는 Later에만 두세요.
- 인수 조건은 정상, 빈 결과 또는 경계, 잘못된 입력, 실패 네 가지를 모두 쓰세요.
- 제가 정하지 않은 것은 "가정"이라고 표시하세요.
대화에만 먼저 보여 주세요.
```

### 5-4b. 업무 규칙 — 화면·서버·데이터가 모두 따르는 약속 (워크북 Day 8)

빈 제목 거절, 상태 3가지, 되돌리기처럼 **화면·서버·데이터가 모두 지켜야 하는 규칙**은 PRD 한 곳에 모아요. 나중에 설계 문서(STEP 7~9)와 시험지(STEP 10)가 이 칸을 기준으로 삼아요.

규칙마다 **"무엇을 보면 지켜졌는지"**를 붙여요.

| 규칙 | 허용/금지 | 확인 가능한 결과 |
|---|---|---|
| 제목이 비었거나 띄어쓰기만 있으면 저장하지 않는다 | | |
| 설명은 비워도 된다 | | |
| 상태는 할 일·진행 중·완료 세 가지다 | | |
| 완료한 카드를 진행 중으로 되돌릴 수 있다 (D-002) | | |
| 삭제 전에 확인한다 | | |

<details>
<summary>👀 예시 답 보기</summary>

| 규칙 | 허용/금지 | 확인 가능한 결과 |
|---|---|---|
| 빈 제목·띄어쓰기만 | 금지 | 카드가 생기지 않고 입력 칸 아래에 이유가 보인다 |
| 설명 비움 | 허용 | 설명 없는 카드가 정상으로 보인다 |
| 상태 3가지 | 허용 범위 | 다른 값은 저장되지 않는다 |
| 완료 → 진행 중 | 허용 | 완료 열 카드를 옮기면 진행 중 열로 간다 |
| 삭제 확인 | 취소면 유지 | 취소를 누르면 카드가 남는다 |

</details>

- claude-code 입력
```claude-code
PRD.md에 "## 업무 규칙" 칸을 추가하려고 합니다. 위 규칙마다 허용/금지와 눈으로 확인할 수 있는 결과를 적은 표 초안을 보여 주세요.
"정상 처리된다"처럼 흐릿한 표현은 쓰지 말고 화면에 무엇이 보이는지로 쓰세요. 4. Task 카드 정보와 상태 규칙과 다른 말을 하지 않게 하세요.
```

> 📌 이후 STEP 14·15에서 기한 초과·정렬·검색 규칙도 **이 칸에** 추가해요.

### 5-5. 열린 질문 정리하기

아직 못 정한 것은 버리지 말고 **"8. 열린 질문과 처리"**에 둬요. PLAN의 "남은 문제"에 있던 요구 관련 질문도 여기로 옮겨요.

- claude-code 입력
```claude-code
지금까지 정하지 못한 요구사항 질문을 PRD.md의 "8. 열린 질문과 처리" 표로 정리하세요.
PLAN.md "남은 문제"에 있는 질문 중 요구사항에 관한 것도 함께 옮기세요. 기술·저장 방식은 STEP 6에서 정하므로 PLAN에 그대로 두세요.
칸: 질문 / 구현을 막는가 / 필요한 정보 또는 검증 / 처리 시점
```

| 예시 질문 | 구현을 막나? |
|---|---|
| 저장 실패 시 쓴 내용을 남길까? | 예 → 지금 정해야 함 |
| 카드 색깔을 바꿀 수 있게 할까? | 아니요 → 다음 버전 |

> ⚠️ **"구현을 막는가 = 예"인 질문이 남아 있으면 PRD를 확정하지 않아요.**
