# STEP 6. ARCHITECTURE.md — "어떤 부품으로 만들지" 설계도 (PLAN P-05)

> **ARCHITECTURE.md** = 구성 요소(부품)는 무엇이고, 각자 무슨 일을 하고, 데이터가 어떻게 흐르는지

## 📚 이 단계에서 참고하는 파일

| 참고 파일 | 무엇을 가져오나 | 왜 참고하나 |
|---|---|---|
| PRD.md | 5. 범위(Must), 6. 인수 조건, 7. 비기능 | **무엇을 만들지** 알아야 필요한 부품을 고를 수 있어요. "새로고침 뒤 유지" 같은 비기능이 저장소가 필요한 이유예요. |
| DECISIONS.md | D-001, D-002 | 결정과 **어긋나는 구조**(예: AI 서비스 연결)를 고르지 않게 해요. 고른 구조는 D-003으로 추가해요. |
| PLAN.md | P-05, 남은 문제("기술·저장 방식 미정") | STEP 4에서 미뤄 둔 질문을 **여기서 해결**해요. |

## 🔗 이 파일을 나중에 참고하는 곳

| 파일·단계 | 무엇을 가져가나 |
|---|---|
| AGENTS.md "환경" | 사용할 기술 (이번 STEP 끝에서 함께 고침) |
| STEP 7~9 설계 문서 | 화면·서버·저장소가 각각 맡는 일 |
| STEP 11 코드 만들기 | frontend·backend 폴더, 기술, 실행 위치 |

---

## 🧸 쉽게 말하면

ARCHITECTURE는 **식당 구조도**예요.

```
🍽️ 식당                         💻 할 일 웹앱
  손님 자리 (주문을 받음)    →    화면 (프론트엔드, React)
  주방 (요리를 만들고 검사)  →    서버 (백엔드, FastAPI)
  냉장고 (재료를 보관)       →    저장소 (SQLite)
```

손님이 "카드 하나 만들어 주세요" 하면: **화면이 주문을 받고 → 서버가 확인하고 → 저장소에 넣어요.**

---

## ❓ 왜 필요할까?

| 설계도가 없으면 | 설계도가 있으면 |
|---|---|
| 화면에서만 검사하고 서버는 검사 안 함 | 누가 어떤 일을 맡는지 정해져 있음 |
| 오류가 나면 어디를 봐야 할지 모름 | "저장 실패는 서버가 알려 준다"처럼 정해져 있음 |
| AI가 마음대로 프로그램을 고름 | 내가 고른 구조만 사용 |

### 대화 1. 설계도가 답해야 할 질문 알기

| 질문 | 식당으로 말하면 |
|---|---|
| ① 사용자의 입력은 어디서 받나? | 주문은 누가 받나? |
| ② 할 일은 어디에 보관하나? | 재료는 어디에 두나? |
| ③ 입력이 맞는지는 어디서 검사하나? | 상한 재료는 누가 걸러 내나? |
| ④ 화면과 저장소는 어떻게 주고받나? | 주문서는 어떻게 전달되나? |
| ⑤ 실패하면 누가 처리하나? | 재료가 떨어지면 누가 손님에게 알리나? |

### 대화 2. 부품 후보 비교 받기 (고르는 건 나!)

- claude-code 입력
```claude-code
확정된 PRD.md와 DECISIONS.md, PLAN.md의 남은 문제를 읽으세요. 할 일 카드 웹앱을 만들 구조 후보를 2~3개 비교해 주세요.
초등학생도 이해할 수 있게, 할 일 카드 하나를 저장하는 과정으로 설명하세요.
비교 기준: Must 기능을 만들 수 있나 / 새로고침 뒤 유지가 되나 / 초보자가 결과를 확인하기 쉬운가 / 나중에 로그인 같은 기능을 붙이기 쉬운가 / 설치가 어려운가
DECISIONS와 어긋나는 후보는 제외하세요. 추천은 해도 되지만 최종 선택은 하지 마세요. 파일은 만들지 마세요.
```

**AI 대답 예시**

| 후보 | 설명 | 좋은 점 | 아쉬운 점 |
|---|---|---|---|
| 브라우저만 | 화면 안에 다 저장 | 간단함 | 다른 컴퓨터에서 못 봄, 로그인 붙이기 어려움 |
| **화면 + 서버 + 저장소 분리** | React 화면, FastAPI 서버, SQLite 저장 | 역할이 나뉘어 오류 찾기 쉬움, 나중에 확장 쉬움 | 실행할 프로그램이 2개 |
| Python 하나로 | 파이썬 하나로 화면과 저장 | Python만 알면 됨 | 화면과 서버 역할을 배우기 어려움 |

> 💡 이 과정의 **기본 선택은 "화면 + 서버 + 저장소 분리"**예요. 다른 걸 고르면 이후 단계를 스스로 바꿔야 해요.

#### 🔄 함께 고치기: 고른 구조는 DECISIONS에 먼저

구조를 고른 **이유**는 DECISIONS, 구조의 **모습**은 ARCHITECTURE에 적어요.

- claude-code 입력
```claude-code
화면(React)·서버(FastAPI)·저장소(SQLite) 분리 구조를 선택합니다. 이유는 역할이 나뉘어 오류를 찾기 쉽고 나중에 로그인을 붙이기 쉬워서입니다.
이 결정을 DECISIONS.md에 D-003으로 추가하세요. 관련 기준 문서는 "ARCHITECTURE.md(작성 예정)"로 적으세요. 바뀐 내용을 보여 주세요.
```

### 대화 3. 설계도 초안 받기

| 칸 | 답하는 질문 |
|---|---|
| 문서 상태 | 초안이야, 확정이야? |
| 적용 범위와 전체 구조 | 어떤 구조를 골랐고 아직 안 정한 건? |
| 기술과 실행 환경 | 무슨 프로그램으로 어디서 돌아가? |
| 구성 요소와 책임 | 누가 무슨 일을 맡고, **무슨 일은 안 맡아?** |
| 주요 데이터 흐름 | 카드 만들기, 상태 바꾸기는 어떤 순서로? |
| 실패 흐름 | 실패하면 어디서 알고 화면엔 뭐가 보여? |
| 승인 확인 | 빠진 건 없어? |
| 상세 설계 연결 | 더 자세한 설계는 어느 파일에? |

- claude-code 입력
```claude-code
확정된 PRD.md와 DECISIONS.md(D-003)를 읽고 ARCHITECTURE.md 초안을 대화에만 보여 주세요.
칸: 문서 상태 / 적용 범위와 전체 구조 / 기술과 실행 환경 / 구성 요소와 책임 / 주요 데이터 흐름 / 실패 흐름 / 승인 확인 / 상세 설계 연결
- 구조를 고른 이유는 쓰지 말고 D-003 번호만 연결하세요.
- 모든 Must 기능에 담당 구성 요소가 있게 하세요.
- 입력 검사는 화면뿐 아니라 서버도 하게 하세요.
- 인터넷에 올리는 방법(호스팅)은 정하지 않았으니 "미정"으로 두세요.
- 화면·API·데이터의 자세한 내용은 쓰지 말고, 어느 파일(SCREEN-SPEC, DATA-MODEL, API-SPEC)에 쓸지만 적으세요.
- 설치나 코드 작성은 하지 마세요.
```

**AI 대답 예시 (일부)**

```markdown
## 구성 요소와 책임
| 구성 요소 | 맡는 일 | 직접 맡지 않는 일 |
|---|---|---|
| 화면 (React) | 입력 받기, 카드 보여 주기, 실패 안내 | 데이터 보관 |
| 서버 (FastAPI) | 입력 검사, 저장 요청 처리 | 화면 그리기 |
| 저장소 (SQLite) | 할 일 보관 | 입력 검사 |

## 주요 데이터 흐름
### Task 생성
1. 사용자가 화면에 제목을 쓰고 저장을 누른다.
2. 화면이 서버에 "이 카드 저장해 줘"라고 요청한다.
3. 서버가 제목이 비어 있지 않은지 검사하고 저장소에 넣는다.
4. 서버가 결과를 알려 주면 화면에 카드가 나타난다.

## 실패 흐름
| 실패 | 감지 위치 | 사용자에게 보이는 결과 | 복구 |
|---|---|---|---|
| 저장 실패 | 화면(서버 응답 없음) | 성공 카드가 생기지 않고 안내가 보임 | 다시 시도, 입력 유지 |
```

> ❓ **"화면에서 막으면 서버는 검사 안 해도 되지 않아요?"**
> 아니요! 손님이 주방에 직접 들어올 수도 있어요. 화면을 거치지 않고 서버에 바로 요청하는 방법도 있어서, **서버도 꼭 검사**해야 해요.
