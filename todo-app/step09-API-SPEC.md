# STEP 9. API-SPEC.md — 화면과 서버의 "주문서 양식" (PLAN P-08)

> **API-SPEC.md** = 화면이 서버에 **무엇을 보내고, 무엇을 돌려받는지**의 약속

## 📚 이 단계에서 참고하는 파일

| 참고 파일 | 무엇을 가져오나 | 왜 참고하나 |
|---|---|---|
| SCREEN-SPEC.md | 화면의 행동(버튼)과 오류 표시 | API는 **사용자 행동**에서 시작해요. 버튼 하나 = 주문서 하나예요. |
| DATA-MODEL.md | 필드 이름과 규칙 | 주문서의 칸 이름을 **그대로** 써야 화면과 서버가 서로 알아들어요. |
| PRD.md | 6. 인수 조건(잘못된 입력·실패) | 실패했을 때 서버가 **무엇을 알려 줄지** 정하는 근거예요. |
| ARCHITECTURE.md | 서버의 책임("입력 검사") | 화면뿐 아니라 **서버도 검사**한다는 근거예요. |

## 🔗 이 파일을 나중에 참고하는 곳

| 파일·단계 | 무엇을 가져가나 |
|---|---|
| STEP 10 TEST-PLAN | 실패 응답 → 시험 문제 |
| STEP 11-3, 11-4 | `/health`, 공통 규칙 |

| STEP 11-6 | 오류 번호(422 등)의 뜻 |

## 🧸 쉽게 말하면

API는 **식당 주문서**예요.

```
🧾 손님(화면)이 주방(서버)에 보내는 주문서

  주문: "카드 하나 만들어 주세요"
  내용: title = 숙제하기, description = 없음

  주방의 대답
   ✅ 성공: "만들었어요! 번호는 7번이에요"
   ❌ 실패: "제목이 비어 있어서 못 만들어요"
```

---

## ❓ 왜 필요할까?

| 정하지 않으면 | 생기는 일 |
|---|---|
| 화면은 "title"을 보내는데 서버는 "name"을 기다림 | 저장이 안 되는데 이유를 모름 |
| 실패했을 때 서버가 무엇을 알려 줄지 안 정함 | 화면에 엉뚱한 메시지 |
| 사용자 행동과 상관없는 기능이 생김 | 필요 없는 코드가 늘어남 |

### 대화 2. 주소(엔드포인트) 정하기

| 하고 싶은 일 | 방법 | 주소 |
|---|---|---|
| 서버 살아 있나? | 보기 (GET) | `/health` |
| 목록 보기 | 보기 (GET) | `/api/tasks` |
| 새로 만들기 | 보내기 (POST) | `/api/tasks` |
| 고치기·상태 바꾸기 | 일부 바꾸기 (PATCH) | `/api/tasks/{번호}` |
| 지우기 | 지우기 (DELETE) | `/api/tasks/{번호}` |

> 💡 외울 필요 없어요. **"어떤 행동이 어느 주소로 가는지"**만 확인하면 돼요.

- claude-code 입력
```claude-code
API 계약에서 정해야 할 것을 비교해 주세요.
- 수정 요청: PUT과 PATCH
- 삭제 성공 응답: 204와 200
- 입력 오류: 전체 오류 하나 / 칸별 오류
- 주소 앞부분: /tasks와 /api/tasks
각각 화면에 어떤 차이가 생기는지 쉽게 설명하고 선택은 기다리세요.
```

- claude-code 입력
```claude-code
제 선택은 PATCH, 204, 칸별 오류, /api/tasks입니다. API-SPEC.md의 "API 계약 결정 기록"에 이유와 함께 적어 주세요.
```

### 대화 3. 초안 받고 네 문서와 맞춰 보기 ⭐

- claude-code 입력
```claude-code
API-SPEC.md 초안을 만들어 주세요.
칸: 사용자 행동 계약 / 공통 규칙 / 엔드포인트 / 요청·응답 예시 / 이번에 구현하지 않는 항목 / API 계약 결정 기록
DATA-MODEL.md의 필드 이름을 그대로 쓰세요. 대화에 먼저 보여 주세요.
```

저장 전에 **네 문서가 같은 말을 하는지** 맞춰 봐요. 이게 가장 중요해요!

- claude-code 입력
```claude-code
"제목을 비워서 저장하는 경우"를 PRD, SCREEN-SPEC, DATA-MODEL, API-SPEC 초안에서 찾아 비교하세요.
문서 위치, 기대 동작, 서로 다른 점을 표로 보여 주세요. 결정을 대신하거나 고치지 마세요.
```

**AI 대답 예시**

| 문서 | 기대 동작 | 다른 점 |
|---|---|---|
| PRD 인수 조건 | 저장 안 됨, 이유 보임 | - |
| SCREEN-SPEC | 입력 칸 아래 이유 표시 | - |
| DATA-MODEL | title 필수, 띄어쓰기만 있으면 안 됨 | - |
| API-SPEC | title 필수인지 **안 적혀 있음** | ⚠️ 빠짐 |

> ❓ **"화면에서 막으면 되잖아요?"** 화면을 거치지 않고 서버에 바로 요청할 수도 있어요. **서버(API)에도 같은 규칙**이 있어야 해요.

- claude-code 입력
```claude-code
API-SPEC에도 "제목이 비거나 띄어쓰기만 있으면 422로 거절하고 칸별 오류를 돌려준다"를 추가하세요.
다시 비교해 차이가 없어졌는지 보여 준 뒤 API-SPEC.md로 저장하세요.
```

## 🔄 함께 고치기

| 이번에 바뀐 것 | 함께 고칠 파일 | 고칠 칸 | 이유 |
|---|---|---|---|
| 비교에서 **다른 문서**가 틀린 걸 발견 | 그 문서 (DATA-MODEL, SCREEN-SPEC …) | 해당 칸 | 순서: DATA → API → SCREEN |
| API-SPEC 생김 | ARCHITECTURE | 상세 설계 연결 | API 설계 위치를 "작성됨"으로 |
| API-SPEC 확정 | PLAN | P-08 상태, 검증 결과, 다음 행동 | 진행 상황 |
| 문서 추가 | README | 프로젝트 문서 | API-SPEC 추가 |

- claude-code 입력
```claude-code
API-SPEC을 확정했으니 함께 고칠 곳을 표로 먼저 보여 주세요.
- 비교 중 발견한 다른 문서의 차이가 남아 있으면 그 문서와 위치
- ARCHITECTURE.md 상세 설계 연결: API = API-SPEC.md (작성됨)
- PLAN.md: P-08 "완료", 실제 검증 결과, 다음 행동 "P-09 TEST-PLAN"
- README.md: 프로젝트 문서에 "API-SPEC.md: 화면과 서버의 약속" 추가
확인하면 고치고 바뀐 줄만 보여 주세요.
```
