# STEP 16. 오류 분석과 디버깅 (워크북 Day 13)

> 버그가 생겼을 때 **추측으로 고치지 않고, 증거로 원인을 좁혀서 작은 수정만** 하는 법을 익혀요.
> STEP 11-6(고장 신고서)의 심화편이에요.

## 📚 이 단계에서 참고하는 파일

| 참고 파일 | 무엇을 가져오나 | 왜 참고하나 |
|---|---|---|
| DEBUG-LAB.md, debug_lab.py (실습 자료) | 세 오류의 격리 재현 | **본 프로젝트를 일부러 고장 내지 않고** 오류를 연습해요. |
| README.md | 릴리스 후보 기준점, 고정 표본 | 출발점과 **재현 데이터**예요. |
| TEST-PLAN.md | 기대 결과 | 버그 보고서의 "기대 결과"를 가져와요. |
| API-SPEC.md | 422·401·404의 뜻, 특수문자 규칙 | 실제 응답이 **약속과 다른지** 판단해요. |
| PLAN.md | 구현 인계 | 수정할 때 쓰는 **수정 승인** 형식이에요. |
| step11-6-errors.md | 고장 신고서, 오류 글자 찾는 곳 | 기본 신고 방법이에요. |

## 🧸 쉽게 말하면

탐정 놀이예요. **"범인은 저 사람이야!"라고 먼저 외치지 않고**, 증거를 모아 용의자를 줄여 가요.

```
증상   "검색했더니 카드가 너무 많이 나왔어요"     ← 사용자가 본 것
오류   "1개 나와야 하는데 6개 나왔어요"           ← 기대와 실제의 차이
원인   "%를 검색 기호로 처리했어요"               ← 증거로 확인한 뒤에만!
```

| 변경 사이클 (STEP 13~15) | 증거 사이클 (STEP 16) |
|---|---|
| 원하는 것에서 출발 | **무엇이 틀렸는지 모르는 상태**에서 출발 |
| 제안 → 영향 → 결정 → 구현 | **재현 → 증거 → 처음 깨진 곳 → 가설 → 작은 수정 → 같은 재현으로 확인** |

## 🗣️ 2. 격리 실습 (P-36) — 일부러 고장 난 작은 모델로 연습

- claude-code 입력
```claude-code
debug-lab/DEBUG-LAB.md와 debug_lab.py를 읽으세요. 본 Task Flow 파일은 바꾸지 마세요.
broken 모드를 실행하고, 세 사례마다 입력·기대·실제·통과 여부를 쉽게 설명하세요.
종료 코드 1은 이 실습에서 의도한 실패이며 설치 오류와 구분하세요.
제가 결과를 확인한 뒤 fixed 모드를 실행하고 차이를 보여 주세요.
```

**리허설 결과**

| 사례 | broken | fixed |
|---|---|---|
| `%` 검색 | A-101, A-102, A-106 (3개) | A-106 (1개) |
| 상태 저장 | 요청 키 `state` → 422, 저장값 TODO | 요청 키 `status` → 200, IN_PROGRESS |
| 만료 안내 | 401인데 "조건에 맞는 Task가 없습니다" | 401이면 "로그인이 만료되었습니다" |

> 💡 **좋은 답**: "사용자 범위는 지켜졌지만 %가 검색 기호로 처리됐습니다."
> **나쁜 답**: "사용자 B의 데이터가 새어 나갔으니 인증을 없애겠습니다." → 출력에 없는 내용이고, 해결책도 아니에요.

## 🗣️ 5. 본 프로젝트에서 같은 행동 해 보기 (P-37) ⭐

> ⚠️ 실습은 실습이에요. **실습에서 오류가 났다고 본 프로젝트에도 있다고 결론 내리지 않아요.** 그리고 **정상인 본 프로젝트를 일부러 고장 내지 않아요.**

- claude-code 입력
```claude-code
실습의 세 행동을 본 프로젝트에서 확인하려고 합니다. 아무것도 수정하지 마세요.

2. 상태를 "진행 중"으로 바꿀 때 화면이 보내는 요청의 칸 이름과 응답 번호
3. 로그인이 만료된 상태에서 목록을 열 때 보이는 문장
제가 직접 따라 할 순서를 알려 주고, 결과를 TEST-PLAN 기대 결과와 비교하는 표를 만들어 주세요.
```

| 행동 | 기대 | 본 프로젝트 실제 | 판정 |

## 🗣️ 6. 처음 깨진 곳 찾기 (계층 지도)

화면에 이상한 결과가 보였다고 **화면 코드가 원인인 건 아니에요.** 단계마다 확인해서 **기대가 처음 깨진 곳**을 찾아요.

```
화면 → Network(요청·응답) → 서버(조건·로그) → 데이터
  ?          ?                    ?              ?
```

| 계층 | 확인한 사실 |
|---|---|
| 화면 | |
| Network | |
| 서버 | |
| 데이터 | |
| **처음 기대가 깨진 곳** | |
| 확신 정도와 이유 | |

<details>
<summary>👀 예시 답 보기 (% 검색 오류)</summary>

| 계층 | 사실 |
|---|---|
| 화면 | 카드 3개 표시 |
| Network | 요청 주소에 `q=%25`(= %)가 그대로 전달, 응답 3개 |
| 서버 | 검색 조건이 `LIKE '%%%'`처럼 만들어짐 |
| 데이터 | "%"가 들어간 카드는 1개 |
| 처음 깨진 곳 | **서버** (요청은 정상, 서버 조건에서 %가 기호로 해석) |
| 확신 | 중간 — 이스케이프 전후 비교는 아직 |

</details>

### traceback(서버 오류 글) 읽는 법

- claude-code 입력 (서버 터미널에 오류 글이 있을 때)
```claude-code
이 traceback을 한 줄로 요약하지 마세요. 오류 이름과 메시지, 우리 프로젝트 파일이 처음 나오는 줄, 호출 경로, 확인할 입력값을 나누세요.
각 해석이 원문 몇 번째 줄에 근거하는지 표시하고 수정은 제안하지 마세요.
[오류 원문 붙여 넣기]
```

> 💡 **맨 아래 줄**이 "무슨 일이 일어났는지", 위로 올라가며 "어떤 길을 지나왔는지"예요. 라이브러리 파일 말고 **우리 파일(taskflow/, src/)이 처음 나오는 줄**을 찾아요.

## 🗣️ 8. 수정 승인 → 새 대화에서 수정 (오류가 있을 때만)

수정 승인은 PLAN "구현 인계" 형식으로 써요.

| 구현 인계 칸 | 수정 승인 내용 |
|---|---|
| 승인한 작업 범위 | 오류 1 하나, 바꿀 파일 |
| 유지할 동작과 금지할 변경 | 사용자 범위, 필터, 정렬, 응답 형식, DB 구조 |
| 읽을 TEST-PLAN 항목 | 실패했던 시나리오 + 관련 시나리오 |
| 확인할 명령 | 같은 재현 순서, 자동 테스트 |
| 중단 조건과 복구 | 다른 곳이 깨지면 멈춤, 마지막 커밋으로 |

- claude-code 입력 (새 대화)
```claude-code
PLAN.md 구현 인계의 오류 한 건만 수정하세요. 먼저 예상 변경(diff)과 실행할 테스트를 보여 주고 승인을 기다리세요.
승인 뒤 수정하고 실제 diff, 테스트 원문, 같은 재현 순서의 결과, 남은 위험을 보고하세요.
무관한 리팩터링, 라이브러리 교체, 새 기능, 인증 완화는 하지 마세요. 테스트를 통과시키려고 기대값을 바꾸지 마세요.
```

> ⚠️ **기대값을 바꿔서 테스트를 통과시키는 것은 고친 게 아니에요.** 승인한 규칙(TEST-PLAN)은 그대로 둬요.
