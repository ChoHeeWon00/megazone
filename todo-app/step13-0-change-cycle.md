# STEP 13-0. 기능 추가의 공통 순서 — "변경 사이클"

> STEP 13~15에서 기능을 3개 더 추가해요. **세 번 모두 같은 순서**로 해요. 이 파일은 그 순서의 지도예요.

## 📚 이 단계에서 참고하는 파일

| 참고 파일 | 무엇을 가져오나 | 왜 참고하나 |
|---|---|---|
| README.md | 제품 기준점 (STEP 12) | 기능을 추가하는 **출발점**이에요. 여기서부터 바꿔요. |
| PRD.md | 보류 기능, Later | 다음에 만들 기능의 **씨앗**이에요. |
| PLAN.md | 다음 행동 | 새 작업 번호를 이어서 붙여요. |
| step00-update-together.md | 함께 고치기 순서 | 변경은 여러 파일을 함께 고치는 일이에요. |

---

## 🧸 쉽게 말하면

**이미 사람이 사는 집에 방을 하나 더 붙이는 공사**예요.

```
새 집 짓기 (STEP 1~12)            방 하나 붙이기 (STEP 13~15)
  빈 땅에서 시작                    사람이 사는 집에서 시작
  무엇이든 정할 수 있음              "원래 되던 것"을 지켜야 함
  망가질 것이 없음                  잘못하면 원래 방까지 무너짐
```

그래서 기능 추가에는 **"바꾸지 않을 것"**과 **"원래 데이터를 지키는 방법"**이 새로 생겨요.

## 🔁 변경 사이클 (10단계)

```
① 진입 검사      출발점(기준점)이 지금도 정상인가?
② 변경 제안      어떤 사용자 문제를 왜 지금 해결하나?          → PRD
③ 영향 지도      어디가 바뀌고, 무엇은 반드시 지키나?          → PLAN
④ 결정           사람이 고를 규칙은?                           → DECISIONS
⑤ 설계 문서      화면·데이터·API를 어떻게 바꾸나?              → SCREEN·DATA·API
⑥ 시험 문제      무엇을 보면 통과인가?                          → TEST-PLAN
⑦ 데이터 이전    기존 데이터를 잃지 않고 바꾸려면? (구조가 바뀔 때만) → DATA-MODEL
⑧ 구현 인계      새 대화의 AI는 무엇만 하나?                    → PLAN
⑨ 구현과 검수    한 단계씩 만들고, 새 기능 + 원래 기능 확인      → PLAN 실제 검증 결과
⑩ 새 기준점      다음 변경의 출발점                             → README, Git 태그
```

> 💡 STEP 1~12와 비교하면 **①, ③, ⑦, ⑨의 "원래 기능 확인"**이 새로 생겼어요. 모두 **원래 되던 것을 지키기** 위한 단계예요.

## 📄 새로 생기는 칸

| 파일 | 새 칸 | 답하는 질문 | 처음 만드는 STEP |
|---|---|---|---|
| PRD | `## 변경 제안` | 어떤 문제를, 무엇으로, 어디까지 해결하나? | 13 |
| PLAN | `## 변경 영향 지도` | 바꿀 것, 지킬 것, 확인할 증거는? | 13 |
| DATA-MODEL | `## 데이터 이전 계획` | 기존 데이터를 어떻게 지키며 바꾸나? | 13 |
| SCREEN-SPEC | `## 가입·로그인·세션 흐름` | 로그인 전후·실패·만료 때 무엇이 보이나? | 13 |
| API-SPEC | `## 변경 검토` | 새 주소, 보호할 주소, 오류 번호는? | 13 |

> 이 칸들은 STEP 14, 15에서 **같은 이름으로 다시 써요.** 이름을 바꾸지 마세요.

### PLAN "변경 영향 지도" 칸

```markdown
## 변경 영향 지도
| 영역 | 바꿀 것 | 그대로 지킬 것 | 확인할 증거 |
|---|---|---|---|
| 화면 | | | |
| API | | | |
| 데이터 | | | |
| 테스트 | | | |
```

> ⚠️ **"그대로 지킬 것"이 비어 있으면 다시 써요.** 이 칸이 비면 새 기능은 되는데 원래 기능이 깨질 수 있어요.
> 💡 "백엔드 수정"처럼 넓게 쓰지 말고 `GET /api/tasks`, `tasks.owner_id`처럼 **찾아서 확인할 수 있는 단위**로 써요.

## 🗣️ 모든 기능 추가의 첫 대화: 진입 검사

**새 대화를 열고** 시작해요. 이전 대화의 아이디어가 섞이지 않게요.

- claude-code 입력
```claude-code
새 대화입니다. 이전 대화를 추측하지 마세요. AGENTS.md를 먼저 읽고, README.md의 제품 기준점과 PLAN.md를 읽으세요.
아직 아무것도 수정하지 마세요. 기능을 추가하기 전에 출발점이 정상인지 확인하려고 합니다.
1. git status와 git log로 기준점 커밋과 지금 상태가 같은지, 커밋하지 않은 변경이 있는지 확인하세요.
2. README의 실행 방법대로 서버와 화면을 켜고 /health를 확인하세요.
3. 제가 브라우저에서 확인할 핵심 시나리오(TEST-PLAN 번호)를 알려 주세요.
결과를 표로 보여 주세요. 칸: 확인 항목 / 방법 / 결과 / 판정
```

- [ ] 커밋하지 않은 변경이 없나요?
- [ ] 핵심 시나리오를 **내가 직접** 확인했나요?
- [ ] 실패가 있으면 **새 기능을 시작하지 않아요.** 원래 있던 오류를 새 기능 탓으로 오해하게 돼요.

- claude-code 입력
```claude-code
진입 검사 결과를 PLAN.md "실제 검증 결과"에 "진입 검사" 활동으로 적으세요. 통과했으면 이번 기능의 작업 번호를 작업 목록 끝에 이어서 추가할 준비를 하세요. 바뀐 줄만 보여 주세요.
```

## 🔄 함께 고치기 — 변경 사이클에서 특히 중요한 것

| 생긴 일 | 고칠 파일 (순서) |
|---|---|
| 변경 제안 확정 | PRD 변경 제안 → PRD 범위·인수 조건 → PLAN 작업 추가 |
| 규칙 결정 | DECISIONS 새 번호 → 관련 설계 문서 |
| DB 구조 변경 | DATA-MODEL 이전 계획 → **백업** → 이전 실행 → 수량 비교 → PLAN 기록 |
| 기능 완료 | PLAN → TEST-PLAN(새 시나리오) → README 제품 기준점(새 기준점) → Git 태그 |
