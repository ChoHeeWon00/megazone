# STEP 17. 자동 테스트·성능 확인·리팩터링 (워크북 Day 14)

> 지금까지는 사람이 눈으로 시험했어요. 이제 **컴퓨터가 매번 대신 시험**하게 만들고, 그 덕분에 **안심하고 코드 정리(리팩터링)**를 해요.

## 📚 이 단계에서 참고하는 파일

| 참고 파일 | 무엇을 가져오나 | 왜 참고하나 |
|---|---|---|
| TEST-PLAN.md | 시나리오, 다음 테스트 입력(STEP 16) | **무엇을 보호할지**의 출처예요. 테스트는 여기서 골라요. |
| PRD.md | Must, 인수 조건 | 깨지면 사용자가 가장 크게 곤란한 행동을 골라요. |
| PLAN.md | 디버깅 기록, 실제 검증 결과 | 실제로 생긴(또는 연습한) 오류를 테스트로 막아요. |
| API-SPEC.md | 응답 번호, 칸별 오류 | 서버 테스트의 **정답**이에요. |
| ARCHITECTURE.md | 구성 요소와 책임 | 리팩터링 뒤 문서와 코드가 같은지 맞춰요. |

## 🧸 쉽게 말하면

**자동 테스트 = 매일 아침 자동으로 문단속을 확인해 주는 경비 로봇**이에요.

```
사람이 확인                       경비 로봇(자동 테스트)
  매번 문 10개를 돌아다니며 확인     명령 한 줄이면 10개를 1초에 확인
  바쁘면 빼먹음                     절대 안 빼먹음
  "어제 됐으니 오늘도 되겠지"        고칠 때마다 다시 확인
```

> 💡 리허설에서 화면 버튼에 "완료**으로**"라는 틀린 글자가 나왔어요. 이 글자를 확인하는 테스트를 만들어 두면, 누가 실수로 다시 바꿔도 **로봇이 바로 알려 줘요.** (실제로 일부러 틀리게 바꿔 보니 테스트가 실패했어요.)

## 🗣️ 1. 지금 상태 확인 (품질 진입 검사)

- claude-code 입력 (새 대화)
```claude-code
새 대화입니다. AGENTS.md, README, PLAN, TEST-PLAN을 읽으세요. 아직 테스트를 추가하거나 코드를 바꾸지 마세요.
지금 있는 자동 테스트 목록과 실행 명령을 확인하고 실제로 실행해 결과 원문을 보여 주세요. 없으면 없다고 하세요.
PLAN.md 작업 목록에 이어서 추가하세요: P-39 보호 행동과 테스트 범위 / P-40 서버 테스트 / P-41 화면 테스트 / P-42 성능 확인 / P-43 리팩터링 한 건과 품질 기준점.
```

> ⚠️ AI가 테스트를 **실행하지 않고 목록만 추측**하면 다시 요청해요.

## ✏️ 2. 깨지면 안 되는 행동 고르기 (P-39) ⭐

"테스트 100개 만들어 줘"가 아니에요. **개수보다 무엇을 지키는지**가 중요해요.

깨지면 사용자가 가장 곤란한 행동을 **내가 먼저** 5~6개 골라요.

| 보호할 행동 | 고른 이유 (근거 문서) |
|---|---|
| | |
| | |
| | |

<details>
<summary>👀 예시 답 보기</summary>

| 보호할 행동 | 근거 |
|---|---|
| 다른 사람의 Task를 보거나 바꿀 수 없다 | STEP 13 (개인 정보) |
| 로그인이 만료되면 빈 목록이 아니라 로그인 안내 | STEP 16 다음 테스트 입력 |
| "%", "_" 검색은 해당 카드만 찾는다 | STEP 16 다음 테스트 입력 |
| 빈 제목·띄어쓰기만 있는 제목은 저장되지 않는다 | PRD 업무 규칙 |
| 제목만 고쳐도 우선순위·마감일이 유지된다 | STEP 14 |
| 기한 초과·정렬 규칙 | STEP 14 |
| 버튼 글자가 올바르다 ("완료로") | 리허설에서 실제로 생긴 오류 |

</details>

- claude-code 입력
```claude-code
제가 고른 보호 행동입니다. [내 표 붙여 넣기]
TEST-PLAN, PRD, PLAN 디버깅 기록을 읽고, 1) 빠진 중요한 행동, 2) 행동마다 확인하기 가장 알맞은 곳(서버 테스트·화면 테스트·사람 확인)과 이유를 표로 제안하세요.
테스트 개수 목표는 두지 말고, 코드는 작성하지 마세요.
```

**테스트 범위** — TEST-PLAN에 새 칸으로 적어요.

```markdown
## 보호할 사용자 행동
## 테스트 범위
- 서버 테스트로 지킬 것: 사용자 분리, 특수문자 검색, 수정 3상태, 정렬, 422 규칙
- 화면 테스트로 지킬 것: 기한 표시, 버튼 글자, 로그인 안 했을 때 로그인 화면
- 사람이 확인할 것과 이유: 320px 배치 (눈으로 봐야 함)
```

> 💡 "자동화하지 않을 것과 이유"도 적어요. 안 적으면 **빠뜨린 건지 일부러 뺀 건지** 몰라요.

## 🗣️ 3. 테스트 한 개의 모양: 준비 → 행동 → 확인

| 칸 | 뜻 | 예 (사용자 분리) |
|---|---|---|
| **준비** | 누구로, 어떤 데이터로 시작? | A의 카드 1개, B 계정 |
| **행동** | 딱 한 가지 행동 | B가 A의 카드 수정 요청 |
| **확인** | 무엇이 보여야 하고, 무엇이 그대로여야? | 404, **A의 카드 내용 그대로** |

> 💡 TEST-PLAN 표의 "시작 조건 / 행동 / 기대 결과"와 같아요. 테스트 번호(test ID) 칸만 추가하면 돼요.

## 🗣️ 4. 서버 테스트 만들기 (P-40)

- claude-code 입력
```claude-code
P-40을 시작합니다. TEST-PLAN의 테스트 범위 중 서버 테스트 항목을 pytest로 만드세요.
- 실제 데이터 파일을 쓰지 말고 테스트용 임시 DB를 쓰세요.
- 테스트마다 준비·행동·확인이 보이게, 이름만 읽어도 무엇을 지키는지 알게 하세요.
- 사용자 A·B를 만드는 준비 코드는 한 곳에 모으세요.
실행 명령과 결과 원문을 보여 주세요. 실패가 있으면 기대값을 바꾸지 말고 보고하세요.
```

**리허설 결과**: 서버 테스트 14개 — 로그인 필수, 두 계정 분리, 로그아웃, 중복 이메일, 만료 세션, 기본값·잘못된 값, 수정 3상태, 정렬(두 번 조회해도 같음), 완료한 일 기한 초과 아님, 검색(제목 또는 설명), "%"·"_", AND 결합, 422, 검색도 내 범위 안.

## 🗣️ 5. 화면 테스트 만들기 (P-41)

- claude-code 입력
```claude-code
P-41을 시작합니다. TEST-PLAN의 화면 테스트 항목을 Vitest와 Testing Library로 만드세요.
사용자가 읽는 글자와 누르는 버튼을 기준으로 확인하세요. (예: "완료로" 버튼이 있고 "완료으로"는 없다)
서버 없이 돌아가도록 서버 응답은 흉내 내세요. npm test 명령을 package.json에 추가하고 결과 원문을 보여 주세요.
```

### ⭐ 테스트가 진짜 지키는지 시험하기

- claude-code 입력
```claude-code
버튼 글자 테스트가 진짜 버그를 잡는지 확인하려고 합니다. 버튼 글자를 일부러 "완료으로"처럼 틀리게 바꾸고 테스트를 실행해 실패하는지 보여 주세요.
확인한 뒤 반드시 원래대로 되돌리고 다시 실행해 모두 통과하는지 보여 주세요.
```

- [ ] 일부러 틀리게 바꾸면 **실패**하나요?
- [ ] 되돌리면 **통과**하나요?

### 실패 출력 읽는 법

| 출력에서 찾을 것 | 뜻 |
|---|---|
| `FAIL` / `×` 옆 테스트 이름 | 어떤 행동이 깨졌나 |
| `Expected` (기대) / `Received` (실제) | 무엇이 달랐나 |
| 파일 이름과 줄 번호 | 어디를 볼까 |

> ⚠️ 테스트가 실패하면 **"제품이 틀렸나, 테스트가 틀렸나"**부터 PRD·TEST-PLAN과 비교해요. 기대값을 바꾸거나 테스트를 지우는 건 마지막 선택이고, 그 전에 **사람이 승인**해요.

## 🗣️ 6. 성능 확인 (P-42) — "느리다"를 숫자로

"앱이 느려요"는 확인할 수 없어요. **측정 질문**으로 바꿔요.

```
❌ 앱이 느려요
✅ 사용자 A가 카드 50개에서 "보고서"로 검색을 적용할 때, 목록 요청이 끝날 때까지 몇 ms 걸리나?
```

- claude-code 입력
```claude-code
P-42를 시작합니다. 위 측정 질문으로 확인하려고 합니다. 코드는 바꾸지 마세요.
제가 브라우저 F12 → Network 탭에서 확인할 순서를 알려 주세요: 데이터 준비, 같은 조건으로 3번 측정, 볼 칸(요청 수, 상태 번호, 크기, 시간).
측정이 끝나면 PLAN.md에 "## 성능 측정" 칸으로 기록하는 형식을 보여 주세요.
```

| 행동 | 데이터 수 | 요청 수 | 상태 | 시간 (3번) | 관찰 |
|---|---|---|---|---|---|
| 검색 적용 | A 50개 | | | | |

> 💡 **한 번의 숫자로 결론 내지 않아요.** 같은 조건으로 여러 번 재요. 적용 한 번에 요청이 2번 가는 것처럼 **이상한 점**을 찾는 게 목적이에요.

## 🗣️ 7. 리팩터링 한 건 (P-43) — 동작은 그대로, 정리만

**리팩터링 = 방 안 물건 위치를 정리하기.** 방을 새로 짓는 게 아니에요. 사용자가 보기에 **아무것도 바뀌면 안 돼요.**

- claude-code 입력
```claude-code
P-43을 시작합니다. 최근 변경 기록과 테스트 결과를 보고, 한 파일이 여러 가지 일을 하거나 같은 코드가 반복되는 곳(코드 스멜) 후보를 3개까지 보여 주세요.
후보마다 불편의 증거, 바꿀 파일, 바뀌지 않아야 할 동작, 위험을 표로 비교하세요.
새 기능, API·DB 변경, 라이브러리 교체는 제외하세요. 한 번에 하나의 작은 리팩터링만 제안하고 코드는 아직 바꾸지 마세요.
```

**리팩터링 승인** (PLAN 구현 인계에 적어요)

| 칸 | 내 승인 |
|---|---|
| 대상 | |
| 동작 불변 조건 | |
| 바꾸지 않을 약속 (API·URL·화면 글자) | |
| 보호 테스트 | 전체 서버·화면 테스트 |
| 실패 시 | 마지막 커밋으로 |

- claude-code 입력
```claude-code
승인한 리팩터링 한 건만 하세요. 바꾸기 전과 후에 서버·화면 테스트를 모두 실행해 결과 원문을 보여 주세요.
측정하지 않은 성능 향상을 주장하지 마세요. ARCHITECTURE.md의 구성 요소와 책임이 실제 코드와 다르면 함께 고칠 내용을 알려 주세요.
```

> 💡 리팩터링 뒤 **API-SPEC이나 PRD를 고쳐야 한다면**, 동작이 바뀐 거예요 → 리팩터링이 아니에요.

## 🔄 함께 고치기 — 품질 기준점

README에 **제품 기준점**("무엇이 되나") 옆에 **품질 기준점**("얼마나 믿을 수 있나")을 추가해요.

```markdown
## 품질 기준점
- 기준 커밋:
- 보호 행동과 테스트:
- 서버 테스트 결과:
- 화면 테스트 결과:
- 성능 측정 조건과 값:
- 리팩터링 내용:
- 사람이 확인하는 항목:
- 판정: 통과 / 수정 후 재검수 / 되돌리기
```

- claude-code 입력
```claude-code
함께 고칠 곳을 표로 먼저 보여 주고 확인하면 고치세요.
- README.md: "## 품질 기준점" (실제 실행한 테스트 결과로), 실행 방법에 테스트 명령 추가
- TEST-PLAN.md: 보호할 사용자 행동, 테스트 범위, 시나리오에 test ID 연결
- ARCHITECTURE.md: 리팩터링으로 바뀐 책임
- PLAN.md: P-39~P-43 "완료", 성능 측정, 다음 행동 "STEP 18 배포 준비"
테스트가 하나라도 실패하면 기준점을 올리지 마세요. "test: add automated tests and quality baseline" 메시지로 커밋하세요.
```
